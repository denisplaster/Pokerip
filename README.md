# RipVault — virtual Pokémon card ripping

RipVault is a full-stack pack-opening and collecting game. You open booster packs with cinematic animations, reveal holo and chase cards, build a collection, trade on a player marketplace, and climb leaderboards.

> **Fictional currency only.** Rip Coins (RC) and all card values are fictional. They can't be purchased, withdrawn, converted to cryptocurrency or exchanged for anything of real-world value. There are no cash prizes or redeemable rewards. RipVault is an unofficial fan project and isn't affiliated with Nintendo, The Pokémon Company, Creatures or GAME FREAK. No official artwork is bundled: cards use placeholder art generated by RipVault (see [Card data & images](#card-data--images)).

## Quick start

**Prerequisites:** Node.js ≥ 20.9 and PostgreSQL 14+ (or Docker).

```bash
# 1. Install dependencies (also generates the Prisma client)
npm install

# 2. Start PostgreSQL (creates `pokerip` and `pokerip_test`)
docker compose up -d
#    …or point DATABASE_URL / DATABASE_URL_TEST at your own Postgres.

# 3. Configure the environment
cp .env.example .env
#    Set AUTH_SECRET (e.g. `openssl rand -base64 32`) and choose SEED_ADMIN_PASSWORD.

# 4. Create the schema and load demo data
npx prisma migrate deploy
npm run db:seed

# 5. Run the app
npm run dev        # http://localhost:3000
```

`db:seed` **wipes** the database in `DATABASE_URL` and loads:

- 26 sets and 316 cards, each with 90 days of reproducible price history
- 7 packs with published odds versions
- 4 mystery boxes and 5 limited collectibles
- 9 missions, 23 achievements and the daily reward calendar
- 24 demo collectors whose pack history was simulated through the real probability engine, so leaderboards, the activity feed and the marketplace (≈130 listings) are populated from the first launch

Demo collectors can't sign in. The admin account comes from `SEED_ADMIN_EMAIL` / `SEED_ADMIN_USERNAME` / `SEED_ADMIN_PASSWORD`. If no password is set, a random one is generated and printed once. No credentials are hard-coded. Create a regular player account at `/register`.

## Testing

**111 tests:** 54 unit and statistical tests, plus 57 integration tests against a real PostgreSQL database.

- **Probability engine** (`tests/unit/probability.test.ts`)
  - Validation: odds must total exactly 1,000,000 ppm, and no tier may have odds but no cards.
  - Roll-boundary mapping and replay of stored rolls.
  - A chi-square fit of rarity and per-card distributions over **1,000,000 simulated cards**, plus a run with the production CSPRNG.
  - A calibration test checking that p-values are uniform across 100 independent seeds, so the RNG and the χ² implementation aren't biased.
  - Simulated mean value matching the analytic expected value.
- **Economy & catalog** (`tests/unit/market-and-economy.test.ts`): market-simulation bounds and mean reversion, reproducible history, ≥300 cards, every seeded pack between 75% and 100% RTP, box odds summing to 100%, redirect sanitising.
- **Progression** (`tests/unit/progression.test.ts`): level curve, UTC streak logic, ISO week keys.
- **Integration** (`tests/integration/*`): uses services and route handlers directly.
  - Atomic wallets and the DB constraints behind them.
  - **Concurrency**: 25 parallel debits, racing double-clicks on "open", six buyers racing for one listing, double-selling a card, double claims.
  - Idempotent replays, vouchers, odds versioning and audit replay.
  - Marketplace rules, instant sells, missions and daily streaks.
  - Limited-supply collectibles, leaderboards and privacy.
  - Admin operations and their audit trail.
  - HTTP guards: 401/403, CSRF origin and content-type checks, Zod validation, rate limiting.

```bash
npm test                    # unit + statistical
npm run test:integration    # needs DATABASE_URL_TEST
```

### Wallet & ledger

Every balance change goes through `applyWalletChange` (`src/server/services/wallet.ts`), inside the caller's transaction:

1. Lock the wallet row with `SELECT … FOR UPDATE`.
2. Reject the change if the balance would go below zero.
3. Update the balance and lifetime totals.
4. Append a `WalletTransaction` row with `balanceBefore`, `balanceAfter`, its type and links to the related pack, card, box or listing.

Postgres backs this up with `CHECK (balance >= 0)` and `CHECK (balanceAfter = balanceBefore + amount)`. Ledger rows can carry a unique idempotency key. Locks are always taken **wallets first** (in sorted user-id order), then users, listings and cards, so two-party flows such as marketplace purchases can't deadlock.

### Probability engine

`src/lib/probability.ts` is a pure module shared by the server, the admin simulator and the tests:

- Odds are integer **parts per million** per rarity tier and must sum to exactly 1,000,000.
- A draw is two rolls: a rarity roll in `[0, 1,000,000)`, then a card roll in `[0, Σ weights of that tier)`.
- `resolveDraw(odds, rarityRoll, cardRoll)` is deterministic, so every stored pull can be **replayed** for audits (`verifyOpening`).
- Production draws use `crypto.randomInt`. The engine never receives the user, their balance or their history, so there are no personalised odds.

### Odds versioning

Editing a pack's odds or pool (or a box's rewards) validates the configuration and writes an immutable `OddsVersion` holding a canonical JSON snapshot and its SHA-256 hash. Draws always use the latest snapshot, and every `PackOpening` and `MysteryBoxOpening` records the version it used. Pack pages show the version history publicly, so odds can't change silently.

### Opening flow

`POST /api/packs/:id/open` with `{ quantity: 1 | 5 | 10, idempotencyKey, useVoucher? }`:

1. If this idempotency key was already used, return the stored result.
2. Draw every card with the CSPRNG from the latest odds version.
3. In **one transaction**:
   1. Debit the wallet, or lock and redeem a voucher.
   2. Insert the openings, rewards (with their rolls) and the owned card copies.
   3. Update counters, missions, achievements and XP/levels, and post big pulls to the activity feed.
4. Return the cards. The client animation starts only after the commit, so it's purely cosmetic.

A concurrent duplicate request hits the unique `(userId, idempotencyKey)` constraint, and the loser returns the winner's result. The client reuses its key after network failures, so a retry can never double-charge.

### Other flows

- **Marketplace:** lock both wallets, then the listing → check `ACTIVE` → move coins (minus the fee) and card ownership → mark the listing `SOLD`. A partial unique index allows only one active listing per card copy.
- **Mystery boxes:** same pattern as packs. Collectible serials are minted under a row lock, and a sold-out collectible pays its published coin fallback.
- **Progression:** `progression.ts` handles missions (`UserMission` per period key, upserted atomically), achievements (insert-or-skip, then reward), XP and levels, and set completion. Rewards are granted inside the same transaction as the action that earned them.

## Economy design

Pack and box returns are tuned to 83–93% expected return-to-player at seed values. The economy drains slowly while daily rewards, missions, achievements and level-ups keep it playable for free. Check it with `npm run economy:report`:

| Pack | Price | Cards | Expected value | RTP |
| --- | --- | --- | --- | --- |
| Starter | 100 RC | 4 | ≈ 86 RC | 86% |
| Trainer | 500 RC | 5 | ≈ 464 RC | 93% |
| Eeveelution | 600 RC | 3 | ≈ 503 RC | 84% |
| Ultra | 1,500 RC | 5 | ≈ 1,314 RC | 88% |
| Inferno | 2,500 RC | 3 | ≈ 2,266 RC | 91% |
| Legendary | 5,000 RC | 5 | ≈ 4,132 RC | 83% |
| Master | 10,000 RC | 3 | ≈ 8,652 RC | 87% |

The Trainer Pack uses the reference distribution from the brief (55 / 25 / 12 / 6 / 1.8 / 0.2%). Within a tier, card weights scale with `value^-0.85`, so a pack's grails stay rarer than its other cards in that tier. Every card's exact probability is published.

Instant sell pays 70% of a card's virtual value; the marketplace fee is 5%. Both rates, level-up rewards and the market-simulation parameters are editable at `/admin/settings`.

## Card data & images

The card APIs (Pokémon TCG API, TCGdex) weren't reachable from the environment this was built in, so the catalog (`prisma/data/catalog.ts`) is a curated demo dataset compiled from public set lists:

- Base Set, Jungle and Fossil in full
- Notable vintage cards
- Modern alternate arts and illustration rares
- A graded vault of PSA-labelled slabs

It includes every card named in the brief (Base Set Charizard, Blastoise and Venusaur, Pikachu Illustrator, Umbreon VMAX, Giratina V and Lugia V alternate arts, Rayquaza VMAX, Gengar VMAX). **No official images are bundled.** Cards render RipVault's own placeholder art: a type-coloured burst, an energy glyph and the Pokédex number.

**Where licensing and API terms permit,** `npm run cards:import` matches cards against [TCGdex](https://tcgdex.dev). It does a dry run by default; `-- --apply` stores artwork URLs. Image hosts are allow-listed in `next.config.ts` and in the admin validator. Values are mock RC amounts, not market prices.

## Scheduled market simulation

Card values follow a mean-reverting random walk in log space. Each tick:

- Moves values by a rarity-specific volatility, clamped to ±15% per tick and to between 0.5× and 2× the card's base value (all configurable).
- Appends a `CardPriceHistory` point with mock volume.

The step size scales with the time since the last tick. There are three ways to run it:

- **Vercel Cron:** `vercel.json` calls `GET /api/cron/market-tick` every 6 hours. Set `CRON_SECRET`; Vercel sends it as a Bearer token.
- **Any scheduler or worker:** `npm run market:tick`, or `npm run market:tick -- --loop --every=60` for a long-running worker.
- **Manually:** the "Run market tick now" button at `/admin/settings`.

## Deployment

### Vercel + managed Postgres (Neon, Supabase, RDS, …)

1. Create a Postgres database and set these environment variables:
   - `DATABASE_URL`
   - `AUTH_SECRET`
   - `CRON_SECRET`
   - optionally the OAuth keys (`AUTH_GITHUB_*`, `AUTH_DISCORD_*`)
2. Run `npx prisma migrate deploy` against the production database, from CI or locally.
3. Optionally seed **once**: `SEED_FORCE=1 NODE_ENV=production npm run db:seed`. Seeding wipes the database.
4. Deploy. `npm run build` runs `prisma generate` automatically, and the cron job in `vercel.json` is picked up.

### Docker

```bash
docker build -t ripvault .
docker run --env-file .env -p 3000:3000 ripvault   # runs `prisma migrate deploy` then `next start`
```

## Security

- **Server-side authority.** Prices, costs, odds, outcomes, payouts and ownership are computed only on the server, and every mutation validates its input with Zod.
- **AuthN/AuthZ.**
  - Sessions are re-validated against the database on every request, so suspensions and role changes apply immediately.
  - Admin APIs and pages check the database role on every request, not only in the layout.
  - Suspended and demo accounts can't sign in.
- **CSRF.** State-changing API calls must be JSON and same-origin (`Origin` checked). Auth.js protects its own endpoints.
- **Rate limits** on sign-in, registration, opening, trading, claiming and admin tools (in-memory; use Redis or Upstash when running several instances).
- **Atomicity.** Row locks, a consistent lock order, idempotency keys, unique constraints and DB `CHECK` constraints prevent double-spends and duplication. All of these are covered by the concurrency tests.
- **Privacy.** Private profiles appear as "Anonymous collector" on leaderboards, in the feed and in marketplace listings and sales. Activity messages never embed usernames.
- **Other hardening:**
  - Passwords are hashed with bcrypt (cost 12), with constant-time behaviour for unknown users.
  - Redirects after sign-in are sanitised.
  - Security headers are set (`X-Frame-Options`, `nosniff`, `Referrer-Policy`, `Permissions-Policy`).
  - Secrets come only from environment variables.
  - Every admin mutation is written to `AdminAuditLog`.

## Known limitations

- Rate limiting and some caches (price changes, settings, compiled odds) are in-process. For multi-instance deployments, move rate limits to Redis and keep the caches short-lived (they already are).
- Leaderboards aggregate on demand. That's fine for thousands of players; at larger scale, materialise them on a schedule.
- No email verification or password reset (no mail provider is configured). Accounts can be managed from the admin dashboard.
- Prisma 7's query interpreter parallelises some nested reads inside transactions, which triggers a harmless `pg` deprecation warning in the test logs.
- A strict Content-Security-Policy (with nonces) isn't configured yet.
